# V1.2 Card Specifications — Persistent Intelligence Memory & GraphRAG

## Document Purpose

This document defines the implementation Cards for **V1.2 — Persistent Intelligence Memory & GraphRAG**.

V1.2 extends the existing Strategic Intelligence system so that intelligence gathered for user-selected companies is not discarded after a single case. Instead, governed research is persisted, reused, projected into a knowledge graph, and queried through an evidence-backed GraphRAG layer.

This document is an implementation specification, not a claim that the functionality already exists.

---

# V1.2 Product Goal

The user researches companies over time, for example:

```text
Capgemini
→ Spotify
→ H&M
→ Ericsson
→ Volvo
→ ...
```

Each researched company contributes reusable intelligence to the user's own persistent knowledge base.

The system should eventually support questions such as:

```text
How are Company A and Company B connected?

Which technologies occur across multiple companies I have researched?

Which companies share the same partners?

Which executives appear across multiple strategic initiatives?

What evidence supports the path between Company A and Company B?
```

The graph must never become an untraceable alternative truth store.

Canonical trust remains:

```text
Source
→ Evidence
→ Claim
→ Verification
→ Governance
```

Graph data is a governed projection over that trust chain.

## Existing Persistence Reconciliation (Proposal Constraint)

G02 must reuse the existing application-owned contracts and repository records;
it must not create a second Source, Evidence, Claim, Verification, or
Governance source of truth. The current V1 persistence already stores:

- `Case` and `WorkflowRun` records, including run timestamps, status, errors,
  snapshots, and accepted checkpoints;
- `Source` records with source/retrieval/publication metadata;
- `Evidence` records linked to Sources, with `extracted_at`;
- `Claim` and `ClaimEvidenceLink` records, with claim `created_at`;
- `VerificationResult` values, including freshness, conflict, duplicate-risk,
  and `verified_at` (currently carried in persisted workflow state);
- `GovernanceDecision` values, with decision status and `decided_at`;
- follow-up research attempts and ordered audit events.

These are reusable as-is as durable research artifacts and provenance links.
G02 still requires a new company-memory index/aggregate, ordered membership,
cross-case research-run association, and memory-first orchestration. G03 owns
new stable entity identities; G04 owns relationship records; G05 owns only a
graph projection/index. Neither may copy or replace canonical trust records.

The existing repository has no durable cross-case company-memory, research-run
history aggregate, entity model, relationship model, or graph projection. Those
are the minimal V1.2 additions; no duplicate versions of existing trust
records are permitted.

## Minimal Temporal Contract (G01/G04/G05)

Reuse existing timezone-aware `datetime` conventions and existing semantic
statuses (`FreshnessStatus`, `VerificationStatus`, and governance PASS /
RESTRICT / BLOCK). Add temporal fields only to the new relationship/projection
records:

```text
relationship_id   required stable relationship projection ID
research_run_id   required; points to the persisted WorkflowRun/run record
created_at        required timezone-aware datetime; record creation time
valid_from        optional timezone-aware datetime; earliest supported validity
valid_to          optional timezone-aware datetime; exclusive end of validity
superseded_by     optional relationship_id; replacement relationship if any
temporal_status   CURRENT | STALE | CONFLICTING | SUPERSEDED
```

`research_run_id` and `created_at` are identity/provenance metadata, not a
second evidence store. `valid_from`/`valid_to` are used only when governed
evidence supports a temporal interval; otherwise they remain unset. A
relationship is CURRENT when its supporting governed claims are eligible and
not stale at the query `as_of`; STALE when the supporting verification/source
freshness is stale; CONFLICTING when supporting governed claims conflict;
SUPERSEDED when `superseded_by` is set. A BLOCK governance decision always
removes the relationship from usable retrieval regardless of temporal status.
Conflicting or stale relationships remain inspectable with qualification but
must not be presented as unqualified current facts. Superseded relationships
remain historical and traceable, never silently deleted.

# Global V1.2 Invariants

The following rules apply to every Card.

## 1. User-Controlled Company Set

Only companies explicitly entered by the user become tracked companies.

The system must not silently invent, recommend, or automatically add target companies to the tracked-company list.

The order in which companies are added must be preserved.

---

## 2. Memory-First Behavior

When a company already exists in persistent intelligence memory, the system should load existing intelligence first.

Repeated web research must not happen automatically merely because the same company is entered again.

An explicit refresh path must exist.

A later freshness policy may recommend or require refresh, but refresh behavior must remain observable and controlled.

---

## 3. Evidence-First Graph Construction

The graph is not the source of truth.

Every usable relationship must be traceable back to governed intelligence.

At minimum, an edge must retain references sufficient to reach:

```text
Relationship
→ Claim
→ Evidence
→ Source
→ Governance Decision
```

---

## 4. Fail-Closed Trust Behavior

Unsupported relationships must not enter usable GraphRAG retrieval.

`BLOCK` information must not be surfaced as usable graph knowledge.

Any use of `RESTRICT` information must remain explicitly qualified and must follow the existing governance contract.

No GraphRAG component may override existing verification or governance outcomes.

---

## 5. Existing V1/V1.1 Behavior Must Remain Intact

V1.2 is an extension.

It must not weaken:

- Source/Evidence/Claim traceability
- Verification
- Governance
- FACT / INFERENCE / RECOMMENDATION distinctions
- privacy restrictions
- fail-closed behavior
- persistence/recovery guarantees already owned by the existing system
- local-first provider behavior

---

## 6. Local-First Scope

V1.2 should begin with the smallest local-first architecture that satisfies the requirements.

A heavy graph database, distributed graph infrastructure, or new cloud dependency must not be introduced unless a Card demonstrates that it is necessary.

---

## 7. Evaluation Before Expansion

GraphRAG is valuable only if it improves relationship-oriented retrieval or produces useful capabilities that the current system cannot provide efficiently.

V1.2 therefore includes an explicit evaluation Card before the feature is considered complete.

---

# G01 — Graph Intelligence Contract

**Dependencies:** None. G01 is the prerequisite contract gate for every later
Card.

## Objective

Define the exact boundaries, data contracts, trust rules, query categories, and evaluation criteria for V1.2 before graph implementation begins.

The purpose of G01 is to prevent GraphRAG from expanding into an undefined knowledge-platform project.

---

## Why This Card Exists

Graph systems become complex quickly when entity types, relationship semantics, refresh behavior, provenance, and query expectations are not fixed early.

G01 establishes a bounded contract so later Cards can be tested against explicit requirements.

---

## In Scope

Define the initial V1.2 contract for:

- tracked companies
- persistent intelligence memory
- entity types
- relationship types
- graph projection
- graph provenance
- GraphRAG retrieval
- refresh semantics
- query categories
- evaluation questions
- success criteria
- explicit non-goals

---

## Initial Entity Types

The first version should support only:

```text
Company
Person
Technology
Project
Event
```

Additional entity types require a future scope decision.

---

## Initial Relationship Types

The first version should support only:

```text
LEADS
PARTNERED_WITH
DEVELOPS
USES
INVOLVED_IN
```

The exact direction and semantic definition of each relationship must be documented.

For example:

```text
Company A --PARTNERED_WITH--> Company B
Person A  --LEADS-----------> Project X
Company A --USES------------> Technology X
```

---

## Relationship Semantics Contract

For each relation type, G01 must define:

- allowed source entity types
- allowed target entity types
- intended meaning
- whether direction matters
- minimum supporting evidence
- whether multiple claims can support the same edge
- how conflicting claims are represented
- how stale relationships are treated

The contract must include temporal provenance fields/semantics (researched-at,
valid-from, valid-to or superseded-by), freshness expectations, and an
inspectable policy for conflicting claims across runs. No temporal conflict
may be silently collapsed.

---

## Memory Contract

G01 must define the expected behavior for:

```text
New company
Existing company
Explicit refresh
Failed refresh
Partial refresh
Duplicate company input
Application restart
```

Expected default:

```text
Company Request
→ Check Persistent Memory
→ If present: load memory
→ If absent: research
→ If refresh explicitly requested: research again
```

Refresh is the only repeat-research path. Existing memory is loaded first and
retains prior runs and their temporal provenance.

---

## Graph Trust Contract

The Card must explicitly define which governed outputs are eligible for graph projection.

At minimum:

- `PASS` relationships may be eligible.
- `BLOCK` relationships are not usable graph knowledge.
- `RESTRICT` behavior must be explicitly defined and qualified.
- unsupported model-generated relations must fail closed.

---

## Query Categories

The initial GraphRAG evaluation should cover:

1. Direct relationship
2. Shared connection
3. Cross-company relationship
4. Neighborhood discovery
5. Recurring entity
6. Multi-hop path

---

## Example Questions

```text
What entities are directly connected to Company A?

Which companies share Technology X?

How are Company A and Company B connected?

Which technologies occur across multiple researched companies?

Which executives occur across multiple projects or events?

What is the evidence-backed path between Company A and Company B?
```

---

## Non-Goals

G01 should explicitly keep these out of V1.2 unless later approved:

- automatic company recommendation
- autonomous crawling of arbitrary companies
- unlimited ontology growth
- social-network scraping
- LinkedIn scraping
- large-scale graph infrastructure
- distributed graph processing
- multi-user graph permissions
- automatic strategic judgment
- automatic actions based on graph findings
- replacing the existing trust pipeline

---

## Deliverables

- written Graph Intelligence contract
- entity schema
- relation schema
- provenance requirements
- memory/refresh rules
- query taxonomy
- evaluation question template
- success criteria
- explicit non-goals

---

## Required Tests / Evidence

Contract-level tests or schema tests should prove that:

- unsupported entity types fail
- unsupported relationship types fail
- invalid source/target combinations fail
- required provenance fields cannot be omitted
- blocked graph material is not eligible for retrieval

---

## Exit Criteria

G01 is complete when the scope is explicit enough that G02–G08 can be implemented without inventing new product semantics during coding.

---

## Main Risks

- ontology becomes too broad
- relationship names are ambiguous
- GraphRAG scope expands into generic enterprise knowledge management
- graph data bypasses governance
- refresh behavior remains undefined

# G02 — Persistent Company Memory

**Dependencies:** G01 only.

## Objective

Create persistent company intelligence memory so research accumulated across cases survives application restarts and can be reused later.

---

## User Story

The user researches:

```text
Capgemini
```

Later researches:

```text
Spotify
H&M
Ericsson
```

When the user returns to Capgemini, existing governed intelligence should be loaded from the application's database rather than automatically repeating web research.

---

## In Scope

Persist and retrieve:

- user-entered company identity
- user-entered display name
- exact and normalized duplicate keys for companies only
- tracked-company order
- first researched timestamp
- last researched timestamp
- research-run history
- associated Sources
- Evidence
- Claims
- Verification Results
- Governance Decisions
- all reusable durable research artifacts and their relationships
- future graph projection status

The implementation must compose the existing `SqliteRepository` records rather
than introduce parallel artifact tables. The minimal new G02 persistence is a
company-memory index (user-entered name plus exact/normalized duplicate key,
ordered insertion), a durable association to existing `WorkflowRun` records,
and retrieval/index metadata for the reusable artifact IDs listed above.

G02 owns durable storage and memory-first orchestration for the complete
reusable research record: Research Runs, Sources, Evidence, Claims,
Verification Results, Governance Decisions, and provenance links. It does not
perform true entity resolution or merge non-company entities; that belongs to
G03.

---

## Required Behavior — New Company

```text
User enters company
→ No canonical company match exists
→ Create tracked-company record
→ Perform normal research workflow
→ Persist governed intelligence
→ Mark company memory available
```

---

## Required Behavior — Existing Company

```text
User enters company
→ Existing canonical company found
→ Load stored intelligence
→ Do not automatically repeat web research
```

The UI or application layer should clearly distinguish:

```text
Loaded from memory
```

from:

```text
New research performed
```

The memory lookup must happen before any provider/research call.

---

## Required Behavior — Explicit Refresh

The user must have an explicit refresh capability.

Expected conceptual flow:

```text
Existing Company
→ Refresh Research
→ New Research Run
→ Existing history retained
→ New governed intelligence persisted
→ Memory updated
```

Refresh must not destroy historical provenance.

Refresh is explicit only; no automatic freshness-triggered web research is
part of G02. A failed or partial refresh leaves prior valid memory and runs
available and marked with its temporal outcome.

---

## Research History

Each company should be able to have multiple research runs.

Conceptually:

```text
Company
├── Research Run 1
├── Research Run 2
└── Research Run 3
```

The system should preserve when each run occurred and which evidence/claims came from each run.

---

## Ordering Requirement

The tracked-company list must preserve user addition order.

Example:

```text
01 Capgemini
02 Spotify
03 H&M
04 Ericsson
```

Sorting by name or timestamp may be offered later, but must not destroy canonical insertion order.

---

## Idempotency Requirement

Repeated submission of the same canonical company must not create uncontrolled duplicate tracked-company records.

---

## Persistence Requirement

Memory must survive:

- app restart
- process restart
- UI restart

The Card is not complete if memory exists only in process state.

---

## Deliverables

- persistent tracked-company model
- company-memory repository/service
- company lookup
- ordered company listing
- memory-first orchestration path
- explicit refresh path
- research-run history
- persistence tests

---

## Required Tests

At minimum:

### New company persists

Research a new company and verify it exists after storage reload.

### Existing company uses memory

Submit the same company again and verify that existing intelligence is loaded without automatically invoking new web research.

### Explicit refresh creates a new research run

Refresh must preserve earlier history.

### Duplicate input is idempotent

Repeated canonical input must not create duplicate company records.

### Ordered list survives restart

Insertion order must remain stable after reopening persistence.

### Failure safety

A failed refresh must not erase previously valid intelligence.

---

## Exit Criteria

G02 is complete when previously researched companies and their governed intelligence can be reopened without re-searching the web.

---

## Main Risks

- duplicate company identities
- accidental overwrite of historical evidence
- refresh silently replacing prior runs
- UI path accidentally triggers research every time
- research artifacts are stored but cannot be reconstructed coherently

---

# G03 — Entity Resolution

**Dependencies:** G02 only.

## Objective

Create stable, reusable entity identities across multiple research runs and companies.

---

## Why This Card Exists

GraphRAG becomes unreliable if the same real-world entity appears as multiple graph nodes.

Example:

```text
Ericsson
Ericsson AB
Telefonaktiebolaget LM Ericsson
```

must not automatically become three unrelated companies when evidence supports that they are the same entity.

---

## In Scope

Resolve the initial entity types:

```text
Company
Person
Technology
Project
Event
```

Every resolved entity receives a stable `entity_id`.

---

## Canonical Entity Record

A conceptual entity record should include enough information to support:

- stable identity
- canonical name
- entity type
- known aliases
- origin/provenance
- created timestamp
- updated timestamp

Exact storage fields may be refined during implementation.

---

## Resolution Principles

### Deterministic evidence before fuzzy assumptions

Exact identifiers and strong evidence should be preferred over model guesses.

### No unsafe merging

If identity is uncertain, retain separate entities rather than silently merging them.

### No uncontrolled duplication

When strong evidence supports equivalence, repeated appearances should resolve to the same entity.

### Human-readable canonical names

The graph UI should display a stable readable canonical name.

---

## Company Resolution Signals

Potential supported signals may include:

- normalized company name
- official domain
- strong source identity
- existing canonical identifiers available in current project data

No external identifier source should be assumed unless explicitly added.

---

## Person Resolution

Person resolution requires special caution.

Same-name people must not be merged solely on name similarity.

Public-professional context may be used only where supported by the existing privacy/governance rules.

---

## Technology / Project / Event Resolution

Normalization rules must be bounded.

Examples:

```text
Google Cloud
Google Cloud Platform
GCP
```

must not be merged merely because an LLM says so unless the resolver has sufficient support.

For V1.2, conservative resolution is preferable to aggressive merging.

---

## Deliverables

- entity model
- stable entity ID strategy
- alias handling
- entity resolver
- conflict/ambiguity behavior
- repository operations
- resolution tests

---

## Required Tests

### Exact repeat

Same canonical input resolves to same entity.

### Supported alias

Known supported alias resolves correctly.

### Ambiguous person

Same name without sufficient support does not silently merge.

### Type safety

A Company cannot accidentally resolve to a Technology or Person.

### Persistence

Resolved IDs remain stable after restart.

### Cross-run reuse

An entity found during one company research run is reused when supported in a later run.

---

## Exit Criteria

G03 is complete when graph nodes can be reused safely across research runs without uncontrolled duplication or unsafe merging.

---

## Main Risks

- aggressive fuzzy matching
- person misidentification
- aliases becoming hidden unsupported assumptions
- entity IDs changing after restart
- entity resolution depending on ephemeral model output

---

# G04 — Governed Relationship Extraction

**Dependencies:** G03 only.

## Objective

Convert governed intelligence into explicit graph relationships while preserving traceability to the original evidence chain.

---

## Core Principle

A relationship is not valid merely because an LLM extracted it.

It must be supported by governed intelligence.

Conceptually:

```text
Source
→ Evidence
→ Claim
→ Verification
→ Governance
→ Relationship Projection
```

---

## In Scope

Initial relation types:

```text
LEADS
PARTNERED_WITH
DEVELOPS
USES
INVOLVED_IN
```

Relationship extraction should use only the bounded ontology defined in G01.

---

## Example

A governed claim may support:

```text
H&M --PARTNERED_WITH--> Google Cloud
```

The graph edge must preserve references to the supporting trust chain.

---

## Minimum Relationship Provenance

A usable relationship should be traceable through fields conceptually equivalent to:

```text
relationship_id
source_entity_id
target_entity_id
relation_type
claim_id
evidence_id
source_id
governance_status
research_run_id
created_at
```

Exact names can align with existing project conventions.

---

## Multiple Evidence Support

A single graph relation may be supported by more than one governed claim.

The model must not require duplicate visual edges merely because multiple sources support the same relation.

Support records should remain inspectable.

Every support record retains temporal provenance (research run and timestamps,
validity/supersession state). Conflicting governed claims remain represented
and inspectable; extraction must not silently choose one as an unqualified
truth.

---

## Conflicting Evidence

If governed claims conflict:

- conflict must not be silently collapsed
- relationship status must remain inspectable
- GraphRAG must not present the relation as unqualified fact if governance does not permit that

---

## `PASS`, `RESTRICT`, `BLOCK`

The exact policy must follow G01 and the existing governance contract.

Minimum hard rule:

```text
BLOCK → not usable GraphRAG knowledge
```

Any `RESTRICT` use must remain qualified and visible.

---

## Extraction Boundary

The Card must not allow unconstrained arbitrary relation generation.

The extractor should map candidate information into the approved ontology and reject unsupported relation types.

---

## Deliverables

- relationship candidate model
- bounded relation extractor
- provenance linker
- governance eligibility check
- relationship support records
- conflict behavior
- extraction tests

---

## Required Tests

### Supported relation

A governed supported claim creates the expected relation.

### Unsupported relation type

Rejected.

### Missing evidence

Fails closed.

### Missing claim

Fails closed.

### BLOCK support

Cannot enter usable graph retrieval.

### Cross-case provenance safety

Relationship links cannot accidentally reference evidence belonging to the wrong company/research chain.

### Duplicate support

New supporting evidence augments an existing relation rather than corrupting or duplicating it incorrectly.

### Conflict handling

Conflicting governed claims do not become an unqualified relation.

---

## Exit Criteria

G04 is complete when every usable graph edge is evidence-backed, governance-aware, and inspectable.

---

## Main Risks

- hallucinated relations
- loss of claim wording/provenance
- graph edges appearing more certain than underlying evidence
- relation duplication
- unsupported cross-case linking

---

# G05 — Knowledge Graph Persistence

**Dependencies:** G04 only.

## Objective

Persist resolved entities and governed relationships as a reusable local knowledge graph.

---

## Important Design Principle

The graph storage layer is a projection over canonical intelligence records.

It must not become an isolated database that cannot be reconciled with the existing Source/Evidence/Claim chain.

---

## Minimum Node Model

Conceptually:

```text
entity_id
entity_type
canonical_name
created_at
updated_at
```

Optional metadata may be added only where useful and governed.

---

## Minimum Edge Model

Conceptually:

```text
relationship_id
source_entity_id
target_entity_id
relation_type
governance_status
created_at
updated_at
```

Evidence support should remain linked through dedicated provenance/support records or equivalent existing models.

---

## Required Capabilities

The graph persistence layer must support:

- create/update node
- create/update relationship
- neighborhood lookup
- relation lookup
- shared-neighbor lookup
- path traversal needed by G06
- provenance lookup
- reconstruction after restart

---

## Storage Decision

G05 should choose the simplest implementation that satisfies V1.2.

Possible implementations may include a relational graph projection, an embedded/local graph representation, or a graph database.

The Card must not assume Neo4j or another graph database unless evaluation shows it is needed.

### Incremental Projection and Update

Projection from canonical governed intelligence is incremental and idempotent.
Each research run can be projected independently; reprojecting the same run
does not duplicate nodes, edges, or support records. Refreshes update only
affected graph records and append temporal provenance. Superseded, invalidated,
or newly BLOCKed support changes graph eligibility without deleting canonical
research history. Projection state must be restart-safe and reconcilable with
the Source → Evidence → Claim → Verification → Governance chain.

---

## Rebuild / Reconciliation

The system should define whether graph state can be deterministically rebuilt from governed canonical records.

Where practical, this is preferable because it keeps canonical intelligence as the source of truth.

---

## Integrity Requirements

The graph must reject or detect:

- orphan edges
- missing entities
- invalid relation types
- invalid provenance references
- duplicate canonical edges where not intended

---

## Deliverables

- graph repository/storage interface
- node persistence
- edge persistence
- graph load/rebuild path
- traversal primitives
- provenance lookup
- integrity tests

---

## Required Tests

### Persistence

Nodes and edges survive restart.

### Orphan protection

Edge cannot point to unknown nodes.

### Provenance integrity

Edge support remains resolvable after restart.

### Rebuild determinism

If graph rebuild is supported, canonical records produce equivalent graph structure.

### Idempotent projection

Reprocessing the same governed relation must not create uncontrolled duplicates.

### Deletion/invalidation behavior

If underlying intelligence becomes invalid or blocked, the graph must not continue surfacing stale usable knowledge without qualification.

---

## Exit Criteria

G05 is complete when the application owns a persistent, integrity-checked graph that remains reconciled with canonical intelligence.

---

## Main Risks

- graph becomes second source of truth
- graph and canonical database diverge
- graph library introduces unnecessary operational complexity
- provenance is lost during graph projection
- update/invalidation semantics are incomplete

---

# G06 — Graph Retrieval & GraphRAG

**Dependencies:** G05 only.

## Objective

Use the accumulated knowledge graph to retrieve relationship-oriented context and produce evidence-backed answers over the user's own intelligence memory.

---

## Core Behavior

GraphRAG should operate over accumulated stored intelligence.

It must not automatically trigger a web search for every graph question.

Conceptual flow:

```text
User Question
→ Entity Resolution
→ Graph Retrieval / bounded Path
→ Supporting Evidence
→ Governed Context
→ LLM Answer
```

This is an evidence-backed GraphRAG boundary. Query classification may be an
internal deterministic step, but the externally meaningful sequence remains
question → entity resolution → graph retrieval/path → supporting evidence →
context → LLM answer. G06 must not trigger automatic web search, Refresh, or
any other research side effect.

---

## Supported Initial Query Types

### Direct Relationship

```text
What connects Company A to Technology X?
```

### Shared Connection

```text
Which companies share the same technology partner?
```

### Neighborhood

```text
What entities are connected to Company A?
```

### Cross-Company Relationship

```text
How are Company A and Company B connected?
```

### Recurring Entity

```text
Which technologies occur across multiple researched companies?
```

### Multi-Hop Path

```text
What evidence-backed path connects Company A to Company B?
```

---

## Retrieval Output

The retrieval layer should return structured graph context, not only a generated paragraph.

Conceptually:

```text
matched_entities
relationships
paths
supporting_claim_ids
supporting_evidence_ids
source_ids
governance_statuses
```

---

## Answer Requirements

Generated answers must:

- stay within retrieved governed context
- distinguish direct and multi-hop relationships
- expose uncertainty/qualification
- include provenance references
- not invent missing graph paths
- clearly say when no supported connection exists

---

## No-Path Behavior

If no supported path exists:

```text
No evidence-backed connection was found in the current intelligence memory.
```

The model must not infer a hidden connection from general knowledge.

---

## Path Bounding

Multi-hop traversal must be bounded.

G01 should define the first maximum hop depth.

V1.2 should prefer a small bounded depth rather than unrestricted graph exploration.

---

## GraphRAG vs Web Research

These are separate capabilities.

```text
GraphRAG
→ asks what is known in persistent intelligence memory

Research / Refresh
→ acquires new public-source intelligence
```

GraphRAG should not silently mutate the knowledge base.

---

## Deliverables

- graph query service
- query-type handling
- bounded path retrieval
- provenance assembly
- GraphRAG context builder
- answer generation contract
- no-path behavior
- retrieval tests

---

## Required Tests

### Direct edge retrieval

Returns correct relationship and provenance.

### Shared connection

Returns only supported shared entities.

### Multi-hop path

Returns a bounded valid path.

### No path

Fails cleanly without hallucinating.

### BLOCK exclusion

Blocked material cannot support an answer.

### Provenance completeness

Every surfaced relation can be traced back to evidence.

### Restart

GraphRAG works from persisted graph after restart.

### No web side effect

Graph query alone must not trigger web research.

---

## Exit Criteria

G06 is complete when the user can ask relationship and multi-hop questions over previously researched companies and receive evidence-backed answers without automatic re-search.

---

## Main Risks

- model answers beyond retrieved graph
- graph paths lack evidence
- traversal becomes unbounded
- GraphRAG silently performs new research
- relation direction is misinterpreted
- answer generation hides restricted/uncertain status

---

## Product Principle

The UI must not become a dense graph dashboard.

Default views should remain clean, with deeper detail progressively disclosed.

```text

04  Ericsson    Researched
```

- last researched date
- stored intelligence availability
- refresh action

Opening a company should show its stored intelligence without triggering a new search.

The user should be able to distinguish:

```text
Stored Intelligence
```

```text
Fresh Research
```

For a company, show governed connected entities.

## Required View 4 — Graph View

# G08 — Evaluation & Portfolio Evidence

**Dependencies:** G07 only.

## Objective

Evaluate whether GraphRAG adds measurable value and package the result into reproducible project evidence suitable for README, CV, LinkedIn, and interviews.

---

## Why This Card Exists

The project should demonstrate more than:

```text
I added a graph.
```

It should demonstrate:

```text
I designed, implemented, and evaluated a governed GraphRAG capability over persistent intelligence.
```

---

## Evaluation Dataset

Create approximately 15–20 fixed evaluation questions.

The dataset should include a balanced subset of:

- direct fact / lookup
- direct relationship
- cross-document relationship
- shared connection
- recurring entity
- multi-hop relationship

Questions must be answerable from the stored test intelligence.

---

## Baseline

The comparison must accurately reflect the existing non-graph retrieval capability.

Do not label the baseline `Hybrid RAG` unless the project actually implements hybrid vector/keyword retrieval.

Use a truthful label such as:

```text
Baseline Memory / Existing Retrieval
vs
Graph Retrieval / GraphRAG
```

---

## Metrics

At minimum:

### Retrieval Relevance

Did retrieval return the information needed for the question?

### Answer Completeness

Did the answer cover the supported connection sufficiently?

### Evidence Traceability

Can every important answer statement be traced to supporting evidence?

### Faithfulness

Does the answer remain inside retrieved governed evidence?

### Latency

How long does retrieval/answering take?

---

## Relationship-Specific Evaluation

GraphRAG should particularly be tested on questions where graph structure should matter:

```text
shared neighbors
cross-company connections
multi-hop paths
recurring technologies
recurring people/projects/events
```

## Acceptance Philosophy

GraphRAG does not have to outperform the baseline on every direct factual question.

A valid outcome may be:

```text
Baseline is equally good or faster for direct facts.
GraphRAG is more complete/useful for relationship and multi-hop questions.
```

The evaluation must report the actual result rather than forcing a positive conclusion.

# Final V1.2 Definition of Done

V1.2 is complete only when all of the following are true:

1. Only user-selected companies enter tracked company memory.
2. Company insertion order persists.
3. Research intelligence survives application restarts.
4. Existing company intelligence loads without automatic re-search.
5. Explicit refresh creates a new research run without destroying history.
6. Entity IDs remain stable across research runs.
7. Supported aliases do not create uncontrolled duplicate nodes.
8. Ambiguous entities fail conservatively rather than being unsafely merged.
9. Relationships use a bounded ontology.
10. Every usable relationship is traceable to governed Claim/Evidence/Source data.
11. `BLOCK` intelligence cannot become usable graph knowledge.
12. Graph state persists or can be deterministically rebuilt from canonical intelligence.
13. GraphRAG supports direct relationship, shared connection, recurring-entity, and bounded multi-hop queries.
14. GraphRAG does not automatically perform live web research.
15. No-path cases fail clearly without hallucinating a connection.
16. The user can visually inspect graph nodes and relationships.
17. The user can inspect provenance for a relationship.
18. The user can open stored company intelligence and explicitly request refresh.
19. A fixed 15–20 question evaluation set exists.
20. GraphRAG is compared against a truthful non-graph baseline.
21. Evaluation measures relevance, completeness, traceability, faithfulness, and latency.
22. Existing V1/V1.1 trust and governance behavior remains intact.
23. README and portfolio claims match measured evidence.
